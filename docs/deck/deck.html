The problem

Agents act for us. Humans are out of the loop.

AI agents now buy subscriptions, read company databases, deploy code and email customers. When one wants to do something risky, someone has to say yes or no, quickly and safely, and that person is rarely at a desk.

Spend

"Research agent wants to spend $50 on a SaaS subscription." Who approves it, and on what evidence?

Data

"Read the customers table (contains PII)." Personal data can leave the organisation in one tool call.

Authority

The agent's sponsor should not approve its own large spend. Roles and separation of duties live in a web console nobody watches.

Manipulation

The agent explains itself, but that text can be prompt-injected. Approvers need facts, not the agent's sales pitch.

What an approver needs
Reach where they are: the phoneContext facts, not the agent's pitchAuthority the right role decidesAssurance it is really them
Result: approvals either block the agent for hours or get rubber-stamped. Neither is human oversight.

The solution

The approval desk moves to your phone

Aegis Pocket is the human-in-the-loop front end for the Aegis gateway (our separate AI guardrails project). The gateway decides that a human must be asked; the phone makes asking fast, informed and safe.
1

Reach the right person

A notification the moment a request needs a human; tap it and the request opens. A home-screen widget shows pending count, blocked threats, redacted personal data and budget left.

2

Decide with facts

Who asked, which sponsor is responsible, amount, failed policy checks, expiry countdown, and a "Why a human is asked" risk score computed on the device.

3

Approve safely

Buttons follow your role (member / admin / owner, two-person rule). Risky approvals need face, fingerprint or PIN. Deny never does: fail-safe direction.

Key flows

Three things the phone does better than a console

Notification → step-up approve

  1. New pending request → Notification Kit notification + in-app banner + haptic cue.
  2. Tap → WantAgent deep link → onNewWant opens the request detail.
  3. Approve on admin / owner / two-person requests or anything ≥ $100 → system face / fingerprint / PIN sheet (ATL3, 32-byte random challenge).
  4. No authenticator (e.g. emulator) → dialog "Device authentication unavailable" with a labelled manual fallback.

Role-locked approvals

  1. Personas: Piotr (member), Emily / Marek (admin), Katarzyna (owner).
  2. $50 subscription needs an admin; $480 seats need owner + admin; budget raise $60 → $150 needs the owner; reading the PII table needs an admin.
  3. Otherwise Approve shows LOCKED with the reason: "Requires owner (you are admin)", "Separation of duties".
  4. Optimistic vote; rolled back with the gateway's reason on 403 / 409.

Risk explainer

  1. Deterministic 0-100 score from the gateway's policy data: control that fired, amount, budget increase, required role, production, sensitive data, data egress, failed checks.
  2. Plain-language reasons; levels low / medium (≥ 30) / high (≥ 60).
  3. The agent's own note is shown, labelled agent-supplied, untrusted, and never scored.
  4. Rule-based on the device: no model, no network.

Reproducibility

From a clean checkout to a running app

git clone https://github.com/JustAnotherDevv/tiles-hackyeah-2026 cd tiles-hackyeah-2026 && ohpm install # build (DevEco Studio 6.1.1, devecocli 1.3.4) devecocli build --modules entry --build-mode debug # sign: DevEco > Project Structure > Signing Configs # (your own Huawei ID; keys stay outside the repo) HAP=entry/build/default/outputs/default/entry-default-signed.hap hdc install -r $HAP hdc shell aa start -a EntryAbility -b com.hackyeah.aegispocket hdc hilog | grep AegisPocket # 17 local unit tests: redactor, eligibility, # step-up rule, risk explainer (README section 8) hvigorw --mode module -p module=entry@default test
  • No server needed: mock mode is the default; live mode needs only the gateway URL in Settings (http://10.0.2.2:8787 on the emulator).
  • Checked by us: build exit 0, lint 0 errors, 17 / 17 unit tests pass. The same source also builds against the OpenHarmony 6.1 SDK (API 23) with no stubs.
  • Honest limits: biometrics and vibration need a real device; background refresh is system-scheduled (~2 h), a safety net, not real-time. See README "Known limitations".
  • Public-safe: empty signingConfigs, no keys or tokens; all mock people and amounts are fictional.
  • AI disclosure: built with Claude Code (Opus 5.5) and the organizers' HarmonyOS skills; logged in AI_WORKFLOW.md. The app itself contains no AI model.

Why it matters

Autonomy for agents. Authority for people.

Human-Centric

Oversight of autonomous AI where people actually are: on the phone, with role rules, separation of duties and accessible controls.

Intelligent

On-device risk explanation that refuses to trust the agent's own words, plus local PII detection with checksums.

Native

Notification Kit, Form Kit, User Authentication Kit, vibrator, WorkScheduler, Network Kit, ArkData, ArkUI. Not portable as-is to another OS.

Next

Push Kit or SSE for instant delivery while closed · wearable target for approve-from-the-wrist · verification on a physical device with biometrics.
